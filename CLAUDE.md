# Vesper Cine — agent notes

Pixel RAW10 → Vulkan → Apple Log cinema camera (Flutter UI + C++ engine). Read
`README.md` (status, testing) and `docs/ARCHITECTURE.md` (pipeline, threads, guard) first.
The owner tests on a **Pixel 10** and is not a programmer: explain results plainly.

## Versioning (required on every change)
After **every** piece of work, bump `version:` in `pubspec.yaml` before committing:
- **minor** (`0.X.0`) for new features or behaviour changes testers will notice;
- **patch** (`0.x.Y`) for fixes, tuning and small UI tweaks;
- always increment the **build number** after `+` by 1.
Mention the new version in the commit message and in the reply to the user.
For user-visible changes also add an entry to `lib/ui/changelog.dart` (shown in Settings › Info › What's new).

## Checks before committing
- `test/native/run_tests.sh` (colour science, native type-check, GPU pipeline on lavapipe, calibration, focus, ISO analysis, sensor calibration statistics + DNG + `sensor.py`)
- `flutter analyze` and `flutter test`; then `git checkout analysis_options.yaml pubspec.lock` (the Flutter tool rewrites them). If `flutter` isn't on PATH, look for an SDK (e.g. `/tmp/flutter/bin`) before concluding Dart can't be checked.
- After editing any `.comp`/`.glsl`: `android/app/src/main/cpp/shaders/compile_shaders.sh` to regenerate the `*_spv.h` headers (green.comp has 4 variants: R16F/RGBA16F × fp32/fp16, plus probe and test-reference variants; 32x16-quad tiles, dispatch width /32).
- New NDK functions used in native code need a declaration in `test/native/android_stubs/`.
- Git: commit and push directly to `main` (owner's choice).

## Builds and testing
- APKs come from GitHub Actions (**Build arm64 APK**, manual `workflow_dispatch`: build_mode, dev_tools). Pushing does not build — if a log looks like an old version, check which commit the latest run used.
- Ask for logs from **Settings › Developer › App log › Copy** (in-app ring buffer, all native log lines since launch). Native logging goes through `vesperLog` (`app_log.h`); new log lines should use the existing `LOGI`/`VK_LOGI`/… macros.
- Profile builds are the test builds (release-speed UI/GPU, dev tools visible).
- **GPU optimisation A/B (opt-in experiments):** a new optimisation goes in behind a `VulkanEngine::kExp*` bit (`setExperiments(mask)`), off by default: a shader `#ifdef` compiled as an extra variant in `compile_shaders.sh`, or an engine branch. List it in `_benchExperiments` (camera_screen.dart); the benchmark runs everything on with each experiment alone and prints `<name>: saves/costs X ms` against the average of the two "Everything on" runs (start and end, so drift cancels). The GPU test prints each experiment's max P010 difference (0 = identical). Once the phone confirms a saving, make it the default code and delete the old path and the bit; drop experiments that don't help.
- **Benchmark validity:** a camera restart mid-run (app left the foreground) re-applies the user's settings, including the guard; the 0.12.2 run on 2 Oct was invalid for that reason (guard paused align/HQ/NR, "savings" of ~5 ms were fake). Since 0.12.3 the benchmark re-asserts guard-off every step and aborts with a message on a restart or any guard-paused stage.
- **GPU A/B Test (0.13.2, Settings › Developer):** for deciding experiments use this, not the long benchmark. Everything on, guard off; blocks normal / exp 1 / normal / exp 2 / … for 3 rounds (0.7 s settle + 0.8 s measure each); each experiment block is compared with the mean of the normal blocks before and after it, printed per round (log tag `VesperAB`). Reason: the 5 Oct 60 fps benchmark drifted +14 ms (26.9 → 41.2 ms, stepwise thermal throttling) and even the linear drift correction gave impossible results ("smooth vignetting saves 3.9 ms").
- **Pass costs:** `setRepeatPass(n)` dispatches a pass (0–4) or part of one (5–8: alignment luma / search, HQ load / load+demosaic via `HQ_PROBE` variants) an extra time per frame without changing the output; the benchmark prints `Pass costs`, `Align` and `HQ` breakdown lines. This replaces per-pass timestamps (useless on this GPU). **Run it at 60 fps**: at 24/30 fps the extra work raises the GPU clock and hides part of the cost.
- Bit-exactness check beyond the unit tests: render several scenes/configs through `VulkanEngine` before and after and compare the P010 byte for byte (a harness of ~150 lines linking `vulkan_engine.cpp`, like `gpu_pipeline_test.cpp`).

## Layout
- `android/app/src/main/cpp/` — native engine: `camera_engine` (Camera2 NDK), `vulkan_engine` (GPU pipeline, submit thread, guard), `shaders/` (unpack, green, align, clean, render), `color_science`, `recorder`, `focus_controller`, `iso_analysis`, `app_log.h`. `native_bridge.cpp` holds the `vesper_*` C exports, `onFrame` and the status JSON.
- `lib/services/vesper_native.dart` — FFI bindings + method channel; `lib/ui/` — Flutter UI (`camera_screen.dart`, `settings_sheet.dart` side-rail settings, `app_log_screen.dart`, `changelog.dart`).
- `android/app/src/main/kotlin/.../MainActivity.kt` — permissions, rotation, viewfinder `SurfaceView` (behind the transparent Flutter surface), `deviceInfo` (version), MediaStore files.
- `tools/calibration/` — per-device calibration: `sensor.py` (no chart: noise, black, clip, linearity, shading, hot pixels from the Dark/White sweeps; phone-side statistics in `sensor_calib.cpp`, DNG writer `dng_writer.cpp`) and ColorChecker colour (`calibrate.py`).

## Current performance facts (Pixel 10, 1080p, 16:9 4000x2256 readout)
- **The GPU clocks down when it has slack**: the same settings measured 33.2–33.9 ms at 24 fps but ~29.6–30 ms at 30 fps (log of 2 Oct 2026, v0.11.3 shaders). Compare costs only at the same frame rate (benchmark at 30 fps); the A/B line in the benchmark is the reliable number. Before 0.12 the guard (85 % = 28.4 ms) paused alignment at 30 fps; since 0.12.0 everything fits (see below).
- Benchmark at **30 fps** (v0.11.4, 2 Oct 2026): base 15.5 ms, sharpening +0.7, HQ +8.0, chroma NR +3.8, TNR +0.4, TNR+align +4.2 (alignment ≈ 3.8), everything on 30.5–31.0. Same at 24 fps (v0.11.3): base 16.1, sharpening +2.8, HQ +11.0, chroma NR +4.7, TNR +3.1, TNR+align +7.0, everything on 33.3–33.6 — the 24 fps deltas are inflated by the lower clock. Repeated runs differ by ~±0.5 ms.
- **Pass costs at 60 fps** (GPU always at full clock; v0.11.5): unpack 1.3, HQ 10.3, alignment 4.8 (≈ 9.6 per run, it runs every other frame), NR (clean) 7.6, render 4.4 ms; everything on ~30–33 ms, ~3 ms not in any pass. At 30 fps everything on (~30.4 ms) is already at full clock, so a GPU clock hint wouldn't help; only light loads clock down (base 15.6 ms at 30 fps vs 11.3 at 60).
- v0.11.6 benchmark (60 / 24 fps): alignment 1/4-res luma from 4 bilinear reads instead of 16 image loads **saves 1.1 / 1.7 ms → default since 0.12.0**. HQ per-tile site scales cost 0.8 / 0.2 ms and alignment best-candidate search split over threads cost 1.5 / saved 0.1 → dropped. Breakdown at 60 fps: alignment = 1/4-res luma 2.3 + search 1.2 ms; HQ = raw load 3.8 + demosaic 3.9 + filter/output 1.9 ms (loading the raw tile is as expensive as the demosaic; per-pixel ALU in the load isn't the cause).
- Guard (0.12.0): first step runs the motion search every 4th frame instead of every 2nd (stage 3, ~1.2 ms); the 85 % margin stays (owner's decision: no lower margin). lavapipe pan test RMS error vs truth: no NR 18.3, unaligned TNR 15.4, aligned 7.0, aligned 1/4 rate 7.9.
- **Confirmed on the phone (v0.12.0, 30 fps, everything on): 27.2–28.4 ms preview, 28.4–29.1 ms while recording (recording adds ~0.7 ms); the guard didn't trigger, 16 s clip = 481 frames, 0 dropped.** The 30 fps goal is met with full-rate alignment; the reduced-rate step is the reserve.
- **HQ lens shading (0.13.3):** green.comp interpolates the shading map per raw pixel between its values at the loaded region's four corners (`sCorner`), matching the quad image's smooth shading. Until 0.13.2 it used one value per 32x32 block, and the mismatch leaked into D = HQ − quad green near strong edges towards the corners (synthetic 3.5× vignette: up to 92–96 codes off an exact per-pixel reference). Corner interpolation vs exact: max 45 codes on the test map, mean error 0.09 codes instead of 0.57, >2-code pixels ~800 instead of ~336 000. **Phone A/B (0.13.2 GPU A/B Test, 60 fps, 5 Oct, no drift 25.1 → 25.1 ms): +0.1 ms (rounds +0.3 −0.1 +0.2)** → default. Exact per-pixel shading (`HQ_EXACT_SHADING`, +3.2 ms) is kept only as the GPU test's reference (`kExpHqExactShading`); exact + 32x16-quad wide tiles (+1.4 ms) was dropped.
- Work-group experiments (0.12.2 → 0.13.0 benchmark at 60 fps, drift-corrected): render 16x8 saves ~0.4–1.3 ms → **default since 0.13.1**; render 16x16 ~0, clean 16x16 +0.4, clean 8x8 +1.7 → dropped. HQ vignetting variants: see HQ lens shading above. **HQ on 32x16-quad tiles is the default since 0.14.1**: GPU A/B Test (60 fps, 5 Oct, drift 25.8 → 26.1) saves 1.4 ms (rounds −1.5 −1.4 −1.4); vs exact shading mean 0.16 codes (16x16 tiles 0.10), 0.054 % > 2 codes (0.051 %), max 68 on the test map's 40-px cells.
- **Benchmark drift:** at 60 fps the phone heats during the ~90 s run ("Everything on" 26.0 → 29.4 ms on 3 Oct). Since 0.13.1 every step is compared with a baseline interpolated between the first and last "Everything on" by its position in the run, and the drift is printed.
- **Long take on a hot phone (3 Oct, right after a 60 fps benchmark; 30 fps AV1, 110 s): 3321 frames, 0 dropped.** The guard went align 1/4 rate → align off → HQ off; HQ then flapped off/on 3× in 20 s (visible sharpness pumping). Since 0.13.1, while recording a stage is restored only with ≥2 ms gap below the 85 % line (trial restores ≥3 ms gap and ≥30 s after the pause) and a flap backs off ≥30 s (up to ~2 min); the back-off resets when the take ends. Restoring mid-take stays (owner's decision).
- **Alignment noise margin (0.14.0):** in dark, noisy tiles (worst towards the frame edges, where lens shading amplifies noise) the motion search picked random offsets — the best of 81 noise-only SADs beats zero by far more than the old fixed 3 % — and TNR dragged the grain around ("swimming" shadows; owner's clip of 5 Oct: noise 2.3 codes mid-frame vs 14.5 at the left edge, alignment on/off confirmed it). align.comp now keeps zero motion unless a candidate wins by 3x the SAD noise std from the noise profile + shading gain (stored per 1/4-res pixel in curLow.g); a motion found at the coarse level is refined freely (a margin there cost the pan test 6.97 → 9.46). GPU test 5b2 measures frame-to-frame movement (8x8 means) on a static dark scene: old 5.48 vs unaligned 3.52 (fails), now 3.52. RMS-vs-truth does not catch it (the smear lowers RMS).
- **Heat safeguard (0.14.0):** `pollHeat()` (native_bridge, from the 250 ms status call on the UI thread, once a second; also while Settings is open during a take) reads `AThermal_getThermalHeadroom(10 s)` (dlsym, API 31) + status → `VulkanEngine::setThermalLevel`: 1 (≥0.8, leave <0.75) no restores; 2 (≥0.9 or MODERATE without forecast) pause the next stage every 15 s (first at once); 3 (SEVERE) everything optional off, take continues. The recorder stops only at CRITICAL (was SEVERE: 3 Oct take stopped at 7:29, 24 fps AV1, 0 drops). Badge WARM/HOT/VERY HOT from `heatLevel`. **Phone test of 0.14.0 (5 Oct, warm start after a 60 fps A/B run, 24 fps AV1):** the forecast works on the Pixel 10 (level 1 at 0.80, level 2 at 0.90 45 s into the take); 15-s steps had align, HQ *and* NR off 93 s in, GPU 31 → 13 ms, yet "severe" still came at 7:00 (0 drops, 10 123 frames; the owner stopped 2 s later, so continuing past severe is still untested). The GPU is only part of the heat (sensor readout, encoder, screen, possibly charging). **0.14.1:** level 2 steps at once, then every 60 s only while the forecast keeps rising (> last step + 0.005), and never pauses NR (only level 3 does).

- Test harness: `ldconfig -p | grep -q` under `pipefail` silently skipped the GPU test now and then (SIGPIPE); fixed in run_tests.sh. If "all GPU pipeline tests passed" is missing from the output, the GPU test didn't run.

Recording power saver (0.13.0, `_powerSaver`): after 10 s of a take the window brightness drops (`setScreenBrightness`) and, in mode 2, `VulkanEngine::setViewfinderPaused` skips the viewfinder output + present (P010 unchanged); a tap on the overlay wakes it for 10 s.
- Gotcha: any change of the viewfinder box size recreates the swapchain (`vkQueueWaitIdle` on the camera thread, ~80 ms → a sensor drop). Keep the box size constant when UI state changes (0.12.1: recording border no longer changes width).
- Memory: the raw upload buffer is already device-local + host-visible (type 1); copying it into a device-only buffer cost 0.7–1.3 ms (v0.11.5, removed).
- Tried: v0.11.3 HQ demosaic on red/blue sites only + sharpening via textureGather: −0.7 to −0.9 ms (kept). v0.11.4 TNR history window reuse (13→9 loads) + clean tile in 16-bit shared memory with precomputed luma: +0.8 ms (reverted). Texture-read counts, idle lanes and shared-memory size are not where the time goes on this GPU — don't optimise from theory.
- 16-bit shader arithmetic is supported (HQ uses the fp16 variant); HQ image format R16F.
- Per-pass GPU timestamps are unreliable on this PowerVR GPU; trust only the frame total. lavapipe timings in tests are meaningless for the phone.
- Camera thread work ~3 ms (memcpy ~2.5 ms). The GPU is the bottleneck, not the CPU.

## Gotchas (learned the hard way)
- Importing RAW10 AHardwareBuffers into Vulkan crashed the gralloc / isn't conformant: keep the memcpy.
- Never block the camera thread on submit/present: that's the submit thread's job. Never let the compositor or Flutter pace the viewfinder.
- Guard costs measured while overloaded are inflated; only restore-time costs are reliable (see ARCHITECTURE).
- Opening Settings pauses processing (not while recording); drop counters reset on pause.
- A 1-quad tile border in green.comp cost +5 ms on the phone: measure on device before assuming a "fold" or merge is faster.
- Recorder (0.13.4 footage-safety review): every stop finalises within ~5 s even with a failed/stuck encoder (stop() joins the recorder thread from the UI thread); codec errors (dequeue < 0 other than the INFO codes) and muxer write errors stop the take with `error: …`; no AAC format 2 s into a take → record without audio (else the video piles up in `pending_` in RAM). Files > 4 GB: AOSP MPEG4Writer (Android 15 source) writes co64 offsets and limits size only by `_PC_FILESIZEBITS`, so long takes should be fine (confirm on the phone). At launch, pending MediaStore entries left by a killed app are published (`recoverRecordings`; no `moov` → `_INCOMPLETE.mp4`).
- Quad image alpha: 1 = clipped highlight, else 0.1 × lens-shading gain (used by NR/sharpen noise models).
